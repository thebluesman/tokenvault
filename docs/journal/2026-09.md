## 2026-09-04

- **[design]** User journeys across Phases 1–9 mapped and published: eight end-to-end flows from first-run setup through edit loops, pull/push, divergence, export, error recovery, and multi-machine state, grounded entirely in the UX specs of the four shipped phases. _Eight journeys read horizontally surface an emergent constraint unseen in any single doc: five independently-deferred features (creation, rename, theme composition, sub-key references, variable creation from pulled tokens) collapse into one shape — Tokenvault can edit what Figma already made, and cannot author anything Figma didn't. None of the five deferrals was wrong; their sum is a boundary._ Serves Phase 10's TBD scope decision. → [docs/ux/user-journeys.md](../ux/user-journeys.md)
- **[design]** Plugin UI dark-mode support scoped as a design spec (Provisional, five open questions in §9). Audit of `src/ui/index.html` found 13 hardcoded color values drifted from documented custom properties; most critical finding: `#fff` serves two roles (base and raised surfaces) requiring a `--bg` / `--bg-raised` split as a dark-mode prerequisite. Recommendation: adopt `figma.showUI(..., { themeColors: true })` as a theme switch with no JS changes (live theme reaction via custom-property cascade). Color semantics preserved (green quieter than amber, red as button-only); dark-mode specifics include role splits (`--accent` / `--accent-text`), 5.4:1 contrast floor for `--ok`, inversion of hover treatment (`brightness` angle flips), and explicit design principle stating plugin chrome follows Figma's theme while token *content* renders at its specified value regardless. _Scoped during Phase 9 error audit; recommends landing before Phase 11 (Figma publishing) to avoid dark-mode as first published bug._ → [docs/ux/dark-mode.md](../ux/dark-mode.md)
- **[design]** Dark-mode design spec finalized — status moved from Provisional to Settled.
